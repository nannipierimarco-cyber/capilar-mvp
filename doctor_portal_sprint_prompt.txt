Implement Sprint: multi-doctor portal and medical review workflow for the capillary MVP.

Context:
The app already has:
- patient quiz;
- Supabase;
- admin;
- AI doctor report;
- patient detail page with AI report;
- checkout/plans flow.

Now we need a doctor portal that can support more than one doctor.

Important business context:
- The platform will have multiple doctors.
- Each doctor needs their own access/login.
- Doctors need a simple dashboard to see assigned patients and upcoming consultations.
- Doctors should see patient intake answers, photos, and AI preliminary report.
- Doctors must be able to enter a medical decision and notes.
- Doctor availability should be supported.
- For now, use Calendly link integration per doctor.
- Do not build a complex scheduling system from scratch yet.
- Calendly can be integrated in two phases:
  Phase 1: store each doctor’s Calendly URL and use it for booking links.
  Phase 2 later: integrate Calendly API/webhooks to sync scheduled appointments.

Goal:
Create a simple but scalable doctor portal with individual doctor accounts, patient assignment, Calendly link support, and medical review workflow.

Compliance/security:
- Do not expose patient data publicly.
- Do not send medical details in email.
- AI report is internal and must be reviewed by doctor.
- AI report is not diagnosis, prescription, or approval.
- The doctor makes the final decision.
- Do not break the existing admin flow.
- Do not expose Supabase service role key to client.
- Keep patient data protected.

Preferred auth:
Use Supabase Auth for doctor login if possible.
If full auth is too complex, implement the database schema and protected doctor routes with a clear temporary fallback, but prefer Supabase Auth.

Roles:
- admin: can see all patients and doctors.
- doctor: can only see patients assigned to them.

1. Database schema

Add or update Supabase schema with:

Table: doctor_profiles
Fields:
- id uuid primary key default gen_random_uuid()
- user_id uuid references auth.users(id) on delete cascade
- full_name text not null
- email text not null
- specialty text
- license_number text
- calendly_url text
- availability_notes text
- max_consultations_per_day integer
- is_active boolean default true
- created_at timestamptz default now()

Table: medical_reviews
Fields:
- id uuid primary key default gen_random_uuid()
- patient_id uuid references public.patients(id) on delete cascade
- intake_id uuid references public.intakes(id) on delete cascade
- doctor_id uuid references public.doctor_profiles(id)
- status text default 'pending_review'
- medical_decision text
- doctor_notes text
- consultation_scheduled_at timestamptz
- calendly_event_url text
- reviewed_at timestamptz
- created_at timestamptz default now()
- updated_at timestamptz default now()

Suggested status values:
- pending_assignment
- pending_booking
- consultation_booked
- pending_review
- needs_more_info
- approved_to_advance
- not_eligible_online
- referred_to_clinic
- completed

If there is already a consultations table that can be reused safely, consider whether to extend it instead of duplicating. But prioritize a clean MVP.

Update supabase/schema.sql with these tables and RLS policies.

RLS:
- admin/service role can read/write all.
- doctors can read their own doctor_profile.
- doctors can read medical_reviews assigned to their doctor_profile.
- doctors can update medical_reviews assigned to them.
- doctors can read related patient/intake/photo/report data only for assigned reviews if feasible.
If RLS becomes too complex, explain what remains, but do not leave routes public.
